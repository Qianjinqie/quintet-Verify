## まず結果から

Fable 5 によるブラインド評価では、本プロジェクトは総合スコア 9.17/10 を獲得し、対戦相手（Fable 5）は 8.0/10 でした — その差は +1.17 です。

3つのタスクすべてで勝利しました：

## 主要な制約

- A は本文を書かない、B はフレームワークを変更しない、C は全文の改訂を提供しない、D は他者の代筆を行わない、E は裁定を直接覆さない。  
- 認知マーカー ✓/?/✗ はプライベートトレースとして存在し、ルーティングの判断には決して入りません。  
- 差し戻しにはアンカー座標を必ず含めること。手戻し作業は指定領域に限定されます（リプル宣言が変更範囲を制約します）。

## なぜ単一の大規模モデルでは足りないのか

単一モデルの「生成＝確定」は、ハルシネーションがエンドポイントまで直通する根本原因です：生成もレビューも確認も自分自身で行う — 監督する側とされる側が同じ立場にあります。Quintet-Verify はこの閉ループを、互いに権限を錠じ合う5つのロールへと分解します —

チェック・アンド・バランスは「自己律」から「他律」へと進化します：監督する側とされる側は立場を共有せず、すべての差し戻しはアンカー座標の中に制約されるため、手戻しによってテキスト全体がドリフトすることはありません。

## コア機能

- **デュアルチャネル認知アーキテクチャ**：ルーティングから見える公開チャネルと、プライベートな Dense Track（✓/?/✗）は物理的に分離されており、3層の保護（構造 / 型 / ランタイムアサーション）によって、プライベートな認知がルーティングに入り込まないことを保証します。  
- **5ロールの厳格なチェック・アンド・バランス**：A (Architect) · B (Executor) · C (Verifier) · D (Judge) · E (Juror) — それぞれに権限と禁則がロックされています。  
- **3つの鉄則（コードで強制）**：① 信頼度の分離 ② 増分修正（アンカー座標＋リプル宣言）③ サーキットブレーカーによる発言禁止命令（max_iterations: 1–10、デフォルト 5。D は発言禁止命令を発令できます）。  
- **強度段階**：low / high（デフォルト）/ max。厳格モードでは、欠陥指摘には影響連鎖を必ず添える必要があり、信頼度が不十分な場合 D は通過させません。  
- **高速モード**：B/C/D のトライアングルのみ。アウトラインなし、アピール分岐なし — 単純なタスクや低コストのシナリオに適しています。  
- **過適合のガバナンス**：C には義務付けられたノルマがありません（欠陥ゼロも許容されますが、カバレッジステートメントを必ず含める必要があります）。D は C を過度に杓子定規だと判断して再審査に差し戻せます（最大2回）。  
- **プラグイン機構**：PLUGINS レジストリ ＋ flags（デフォルトはすべてオフ）。オプションの qv_extras.py は標準化された pre/post_act_hooks を通じてマウントできます — 詳細は[プラグイン](#プラグイン)を参照。  
- **カスタマイズ可能なワークフロー（v1.4）**：ワークフロー定義のフロントエンド編集、新しいロールの作成と AE 権限の継承、静的検証、ロールごとの独立した LLM 設定。

## 他のマルチエージェントフレームワークとはどう違うのか

- **AutoGen / CrewAI / MetaGPT**：いずれもマルチエージェント協調をサポートしモデル非依存ですが、3つの能力が欠けています。推論時の厳格なチェック・アンド・バランス、プライベートな認知トレースの監査、増分修正（トークン節約）です。  
- **Quintet-Verify**：マルチエージェント協調とモデル非依存をサポートした上で、さらに以下を提供します：  
  - 推論時の厳格なチェック・アンド・バランス（法廷型の権限錠じ込み）  
  - 監査可能なプライベート認知トレース（Dense Track）  
  - 増分修正（アンカー座標＋リプル宣言。平均約80%のコンテキストを節約）

多くのフレームワークは「AI に協調させる」ことを行い、Quintet-Verify は「AI に互いを牽制させる」ことを行います — 前者が追求するのは出力の効率、後者が追求するのは結論の信頼性です。

## 品質に関する説明

単一モデルを直接使う場合と比べて、Quintet-Verify の利得は構造的なチェック・アンド・バランスから来るものであり、パラメータ数の増大から来るものではありません：

- **純粋なモデルとの比較**：ハルシネーションはもはやエンドポイントまで直通しません — まず C のレビューと D の裁定を通らねばならず、すべての差し戻しはアンカー座標の中に制約されます。C の「欠陥ゼロ」の結論と D の過適合判定は、「やみくもに揚げ足取りをする」ような内輪揉めも同時に防ぎます。  
- **純粋な J-Space との比較**：J-Space の密な認知管理は単一モデルの内部で動作し、自己監督の上限は「自分で自分を捕まえる」ことです。Quintet-Verify は ✓/?/✗ をプライベートな認知トレースとして保持しつつ、裁定権限を独立したロールに委譲します — チェック・アンド・バランスを自己律から他律へと引き上げます。

以上はメカニズムレベルでの定性的比較であり、実用上の有効性は一般にベースモデルをはるかに上回ります — 詳細は「まず結果から」を参照してください。

### 最小限の例 (実際のLLM)

```python
from quintet_verify import (
    DEFAULT_FLAGS,
    LLMConfig,
    PublicState,
    QuintetState,
    build_graph,
    build_llm_agents,
)

# 1. モデルを設定する（OpenAI互換エンドポイント。共有またはロールごと）
cfg = LLMConfig(
    api_key="sk-...",
    base_url="https://api.deepseek.com/v1",
    model="deepseek-chat",
)
agents = build_llm_agents(cfg)  # 5つのロール（A, B, C, D, E）を返す

# 2. グラフを構築して実行する（interrupt_before_e=False は、ユーザーフィードバックのために E の前で一時停止しないことを意味する）
graph = build_graph(*agents, interrupt_before_e=False)
final = graph.invoke(
    QuintetState(
        public=PublicState(
            task="Evaluate the feasibility of a technical solution and provide a conclusion.",
            user_satisfied=True,   # 満足 → E が裁定に同意し、ワークフローが終了
            intensity="high",      # 強度段階：low / high / max
            flags=dict(DEFAULT_FLAGS),  # プラグインのスイッチ。デフォルトはすべてオフ
        )
    )
)

# 3. 結果を読み取る
pub = final["public"]
print(pub.verdict.approved, pub.verdict.confidence_score)  # D の裁定と信頼度
for section in pub.draft.sections:
    print(section.anchor_id, section.content)
```

## 理論的背景と独立性に関する声明

### インスピレーション

Quintet-Verify は、以下の点で先行する研究からインスピレーションを得ています：

· 認知マーカー記号（✓/?/✗）と「プライベートな認知トレース」（Dense Track）の命名：J-Space Cognition Suite V3.6（doi:10.5281/zenodo.21971181）に由来します。同研究は、単一モデルの内部でコンパクトな記号を使って認知状態を管理する手法を最初に体系的に提案し、「内省的マーカー」が推論品質に与える好影響を検証しました。
· マルチロールの法廷型チェック・アンド・バランスという組織形態：b23.tv/z3C0vVM で公開された Quintet Verification マルチモデル討論システムに着想を得ています。同システムは「ロール分離と異議手続きを通じて、生成時のハルシネーションをコンセンサスゲームへ変換する」ことの実現可能性を実証しました。

上記の研究・作品のオリジナルな貢献に対して、敬意と感謝を表します。

### 根本的なアーキテクチャの違い

Quintet-Verify は J-Space から記号の命名を、Quintet Verification から組織形態を借用していますが、その基盤となる認知アーキテクチャは両者といずれも還元できないほど異なっています。これらの違いは漸進的な改善ではなく、認知主体・情報トポロジー・制御の性質という3つの根本前提の再定義です。

| 観点 | J-Space（グローバルワークスペース理論） | Quintet Verification（マルチモデル討論） | Quintet-Verify（アンカー型認知理論） |
|---|---|---|---|
| 認知主体 | 単一モデルの内部 | 複数の独立したモデル（ステートレス） | 複数の独立したエージェント（それぞれがプライベートな状態を持つ） |
| 認知状態の担体 | グローバルなコンテキストウィンドウ | 各モデルの独立した出力 | 公開の共有状態＋プライベートトレース（物理的に分離） |
| 情報フロー | グローバルブロードキャスト＋競合アクセス | 討論型のフル伝送 | アンカー参照（共有事実は anchor_id + checksum 経由） |
| 修正メカニズム | 全文書き換え（内省による修正に依存） | 全文書き換え（討論による修正に依存） | 増分修正（精密な座標＋リプル宣言） |
| 制御の性質 | プロンプト主導のソフト制約 | プロンプト主導のソフト制約 | コンパイル時検証＋ルーティングガード（ハード制約） |
| リカバリ機構 | テキスト台帳のロールバック | 標準化されたリカバリなし | アトミックな状態チェックポイント（任意のラウンドへの正確なロールバック） |
| チェック・アンド・バランス | 自己監督（同じ立場） | クロスモデル討論（独立した立場） | 権限錠じ込み＋法廷手続き（立場の分離＋手続きの厳格性） |
| 監査可能性 | 思考連鎖のテキスト（非構造的なロールバック） | 討論テキスト（非構造的なロールバック） | 構造化された Dense Track 監査（✓ の検証証拠と ✗ の反証証拠を追跡可能） |

### 中核的な違いの要約

· J-Space が扱うのは「一人の人間がどうすればより良く考えられるか」（単一意識の深い内省）。
· Quintet Verification が扱うのは「集団がどう討論を通じて合意に達するか」（複数の立場による外的チェック）。
· Quintet-Verify が扱うのは「独立した認知状態を持つエージェントの集団が、厳格なルールを通じてどう検証可能な結論へ収束するか」（分散認知の憲法的ガバナンス）。

Quintet-Verify の独自の貢献は、「プライベートな認知トレース（Dense Track）」と「厳格な権限マトリクス」を初めて組み合わせたことにあります。これにより、マルチエージェントシステムは個々の推論の深さを維持したまま、監査可能で追跡可能かつ強制的に停止できるシステムレベルの信頼性を達成できます。

### 独立性に関する声明

上記の根本的なアーキテクチャの違いに基づき、Quintet-Verify はここに宣言します：

· 派生作品ではない：Quintet-Verify は J-Space Cognition Suite V3.6 の派生作品でもフォークでもありません。両者は完全に異なるコード実装、認知トポロジー、制御哲学を採用しています。
· 独自の知的財産：Quintet-Verify のコードはすべて私たちのチームが独自に執筆したものであり、J-Space または Quintet Verification のソースコード、プロンプトテンプレート、プロトコル文を一切コピー・翻訳していません。
